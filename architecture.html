SYSTEM ARCHITECTURE

From decrypted ELF to native execution.

The pipeline links analysis, PPU lifting, native builds and a developing guest runtime. Each boundary needs separate tests; diagrams do not imply compatibility.

01 / PIPELINE

The recompilation path

flowchart TD
  ELF[Decrypted ELF] --> LOAD[ELF loader and guest address map]
  LOAD --> ANALYSE[Analysis and control-flow recovery]
  ANALYSE --> PPU[PPU decoder and lifter]
  PPU --> CPP[Generated C++]
  CPP --> BUILD[Native Windows build]
  BUILD --> RT[PS3RT runtime]
  RT --> HLE[LV2 / PRX / NID services]
  RT --> SPU[SPU / MFC / DMA]
  RT --> RSX[RSX / GCM command processing]
  RSX --> D3D[Direct3D 11 host backend]
  HLE --> TEST[Strict faults, tests and title evidence]
  SPU --> TEST
  D3D --> TEST
02 / SUBSYSTEMS

Independent correctness boundaries

PPU and native code

Instruction decode, control flow, CR/LR/CTR/XER, loads/stores, VMX/FP behavior and generated-code validity need semantic tests.

Runtime and HLE

Guest memory, imports, NIDs, LV2, PRX loading, threads, filesystem, audio, input and save data must match guest expectations.

SPU and MFC

Execution, DMA tags and completion order, atomics and SPURS lifecycle remain correctness-sensitive.

RSX and GCM

FIFO GET/PUT, method decoding, resources, shaders, textures, render targets and presentation must work for title-authored commands.

Host build

Successful compilation confirms a build stage only; it does not validate guest semantics or execution.

Validation

Reproducible logs, strict-fault runs, subsystem tests and per-title outcomes provide evidence for status changes.

03 / CRITICAL PATH

What must work next

The canonical roadmap highlights PPU recovery and semantics, null-loop escape without invented success, FIFO GET/PUT correctness, guest PUT progress without boot assist, and title-authored draws/shaders.
