01 / PROJECT

What is PPSX33?

PPSX33 is an experimental PlayStation 3 full-recompilation project focused on translating supported PS3 executable code into native Windows builds and rebuilding the runtime behavior those programs depend on.

Primary objective

Full PS3 game recompilation is the engineering direction, not a claim that every title is currently compatible or playable. A successful lift, generated executable, window or diagnostic draw is not proof of a working game.

Project typeStatic recompiler and host runtime research
Guest platformPlayStation 3 / Cell Broadband Engine
Host targetWindows x64
Graphics directionVulkan 1.2 default host path; OpenGL secondary

The project is a whole-system effort. Translating PPU instructions is only one part. A title may also depend on LV2 kernel calls, PRX modules, NID imports, SPU programs, MFC/DMA ordering, SPURS scheduling, cell libraries, filesystem behavior, RSX/GCM commands, shaders, audio, input and save services.

Core principles

  • Keep decode coverage, translation coverage, semantic correctness, runtime correctness and game compatibility separate.
  • Unsupported behavior must remain visible in diagnostics rather than silently becoming success.
  • Record source revision, build configuration, input identity when safe, logs and repeatable test steps.
  • Prefer correctness and conformance evidence before optimization or compatibility claims.
02 / WORKFLOW

Recompiler pipeline

The application turns a supported decrypted ELF into generated host code, links the runtime and then validates observable behavior.

INPUTDecrypted ELFELF64, big-endian PowerPC64
↓
ANALYSISLoader and analysisSegments, entry point, symbols, OPD and module hints
↓
TRANSLATIONPPU decode and liftSupported guest regions emitted as C/C++
↓
HOST BUILDMSVC toolchainCompile and link game objects with runtime
↓
EXECUTIONNative game buildPS3RT supplies guest runtime services
↓
VALIDATIONTests and title evidencePPU, SPU, HLE, RSX, input, audio and sustained behavior

What each stage proves

  • ELF load: the parser accepted the input structure.
  • Lift: the lifter emitted code for recognized regions. This alone does not prove instruction semantics.
  • Host build: generated code and runtime linked for the selected host configuration.
  • Launch: the host process started and runtime initialization progressed.
  • Game behavior: only a repeatable title test can establish boot, menu, rendering, input, audio or playability.

04 / PROCESSOR

PPU and PowerPC translation

The PPU is the main PowerPC processor. PPSX33 decodes guest instructions and emits host C/C++ for supported regions.

Responsibilities

  • Parse the ELF entry point, loadable segments and relevant metadata.
  • Decode 64-bit PowerPC instruction forms and emit host-side operations.
  • Preserve guest register state, branches, condition register behavior and calling conventions.
  • Handle memory access, endianness, load/store semantics, floating point and VMX behavior.
  • Represent external calls, imports and function descriptors without inventing targets.

Correctness-sensitive state

StateWhy it matters
GPR / FPRInteger and floating-point guest register values.
CRCondition fields used by conditional branches and record-form instructions.
LR / CTRLink and count registers used by calls, returns and branch patterns.
XERCarry, overflow and summary-overflow state.
FPSCR / VMXFloating-point status and vector behavior.
Guest memoryAddress translation, access checks and big-endian data representation.

A translated instruction count is not a semantic test. For opcode changes, isolate the operation, check architectural side effects, add synthetic regression coverage and rerun relevant tests. See PPU coverage notes.

05 / PROCESSOR

SPU, MFC, DMA and SPURS

SPU programs are specialized 128-bit SIMD workloads. Their correctness depends on local-store execution and explicit communication with memory and other processors.

SPU executionInstruction decoding, register state, channels, mailboxes and local store.
MFCMemory flow controller operations, tags, completion and ordering.
DMATransfer sizes, alignment, list operations, stalls and completion visibility.
SPURSWorkload/job lifecycle and scheduling behavior.

Timing and ordering are part of the guest-visible contract. A transfer that appears to work in a simple test may still fail when a title waits on tags, reuses a buffer or schedules multiple jobs. Keep interpreter coverage, DMA semantics and SPURS lifecycle tests distinct.

06 / GRAPHICS

RSX, GCM and host graphics

The RSX path must interpret the guest command interface and reproduce the resources and synchronization required by a real title.

GUESTGCM controlGET / PUT / FIFO RAM
→
DECODEMethod processorState and command validation
→
RENDERRSX resourcesBuffers, textures, shaders, surfaces
→
HOSTVulkan presentSwapchain and presentation

The repository documents a Vulkan 1.2 host baseline with swapchain presentation and guest RGBA upload paths. OpenGL is a secondary path; Direct3D 11 was removed from the current roadmap. A diagnostic or boot-assist draw validates only the host rendering path. Real title rendering requires guest-authored FIFO progress, command decoding, correct resources, shader translation and synchronization.

Graphics validation checklist

  • GET/PUT behavior and command boundaries are consistent.
  • Methods are decoded from the guest command stream, not only injected probes.
  • Vertex/index data, textures, formats and render targets are valid.
  • Shader behavior, depth, blend and synchronization match the title's expectations.
  • Frames are repeatable and correspond to actual guest work.

08 / APPLICATION

GUI and user workflow

The Windows Forms application organizes a per-game project from input through analysis, generated code, build and runtime reports.

  1. Load ELFSelect a decrypted ELF file you are legally entitled to use. PPSX33 does not decrypt retail EBOOT files.
  2. Decompile / liftRun analysis and emit generated C++ plus lift and analysis reports into the project codebase.
  3. ConfigureReview project settings and controller bindings before the build workflow locks the mapping.
  4. BuildUse the configured Microsoft C++ toolchain to compile and link game objects with PS3RT.
  5. RunLaunch the generated executable and inspect runtime logs and the first failure.
  6. ReportKeep build, lift and runtime evidence with the project so failures can be reproduced.

Projects are created beneath build/dist/projects/<name>/ with input/, codebase/ and output/ directories. Build progress estimated from object-file timestamps is advisory, not authoritative compiler progress. Decompilation is synchronous and is not currently described as cancellable. A cancelled build may clear generated project folders, requiring the ELF to be loaded again.

Controller mapping

The Controller Studio is hosted in WebView2. Defaults are defined in src/gui/KeyMap.cs, settings are stored in %APPDATA%/PPSX33/settings.json, and the host persists the project's output/pad_map.json. See the complete key mapping.

12 / EVIDENCE

Coverage, reports and compatibility

PPSX33 records static-lift snapshots, but a 100% translated count is not a 100% correctness or compatibility result.

The repository's PPU coverage report includes recorded snapshots for God of War III, Minecraft (PS3), Uncharted 2, Demon's Souls, Grand Theft Auto: San Andreas and Grand Theft Auto V. Those tables report instruction instances, translated instances, unimplemented instances, chunks and ELF metadata. Values are tied to the specific analyzed inputs and must not be generalized to other builds or game versions.

Decode coverageWas the instruction encoding recognized?
Translation coverageWas host code emitted for the instruction instance?
Semantic correctnessDoes the emitted behavior match the PowerPC architecture?
Runtime correctnessDo generated code and host services behave correctly?
Game compatibilityDoes a repeatable title path operate correctly?

OPD and PRX/module string counts may be heuristic. Zero detected symbols does not mean there are no functions. Approximate operations or no-op fallbacks may still be counted as translated. See the full coverage report and per-game records.

13 / CONTRIBUTING

Developer guide

Changes should be small, testable and documented against the current source tree.

  1. Find the ownerIdentify the subsystem and its current implementation path before editing.
  2. Confirm semanticsCheck architecture specifications, API contracts and existing helper behavior.
  3. Write a focused testBuild a synthetic regression case that isolates the behavior being changed.
  4. Run affected checksRun smoke tests, regression tests and a clean build where available.
  5. Preserve evidenceCapture the exact command, result, toolchain and limitations.
  6. Update documentationKeep source layout, roadmap, coverage and title notes consistent with verified behavior.

For a PPU opcode change, inspect src/core/ppu_lifter.cpp, relevant PPU runtime helpers and architectural side effects such as CR, XER, carry, overflow, memory and endianness. Do not replace an unsupported operation with a silent no-op.

For changes to src/core/ps3core.h, update the implementation, CLI callers and C# P/Invoke declarations in src/gui/Native.cs. Keep types, ownership, return values and error handling consistent.

14 / SETUP

Requirements and build setup

The documented host target is Windows x64 with the Microsoft C++ toolchain and the .NET SDK used by the GUI.

Build outputs are documented under build/dist/, including PS3Recomp.exe, ps3core.dll, ps3rt.dll and import artifacts. Release packaging must be checked on a clean Windows machine. Verify the GUI starts, CLI help works and the synthetic smoke test passes. Do not claim an unrun check.

Linux and macOS are not current supported host-runtime targets. Toolchain requirements can change; check the repository build files and engineering notes.

15 / RESPONSIBLE USE

Legal and responsible use

PPSX33 does not bundle commercial game files, firmware or proprietary decryption keys.

  • Use only files and data you are authorized to access and process under applicable law and relevant license/platform terms.
  • Owning a disc or copy does not automatically resolve every legal question about decryption, circumvention or derivative output.
  • PPSX33 loads decrypted ELF files only. It does not decrypt EBOOTs or provide decryption keys.
  • Do not distribute game binaries, extracted assets, firmware or keys through the project.
  • Audit image, font, icon, library and other third-party asset provenance and redistribution terms before packaging.
  • PPSX33 is independent and is not an official Sony product. PlayStation marks remain with their owners.

Read the repository's legal notes, terms, security policy and license.

16 / REFERENCE

Glossary and source references

A compact index of terms used throughout the recompiler and runtime.

ELF
Executable and Linkable Format used for guest input.
PPU
Power Processing Unit, the PS3's main PowerPC processor.
SPU
Synergistic Processing Unit for specialized parallel workloads.
MFC
Memory Flow Controller used by SPUs for memory transfers and synchronization.
DMA
Direct Memory Access transfer operations.
SPURS
PS3 workload/job management framework used by SPU workloads.
RSX
PS3 graphics processor.
GCM
Graphics command interface and FIFO control path.
LV2
PS3 kernel and system-call layer.
PRX
PS3 module format and runtime module-loading concept.
NID
Numeric identifier used to resolve imported system functions.
HLE
High-level emulation or reimplementation of guest system services.
OPD
PowerPC64 function descriptor structure used for indirect calls.
VMX
PowerPC vector/SIMD instruction facility.
FIFO
First-in, first-out command stream used by the graphics interface.
