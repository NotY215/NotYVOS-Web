01 · PROJECT

What is NotYVOS?

NotYVOS is a freestanding x86-64 operating system with a native kernel, userland, VFS, persistent NYFS storage, software-rendered desktop, hardware drivers and a PS3 runtime foundation. The project is not a themed Linux distribution. Its core objective is a native platform where the low-level execution path, storage path, rendering path and runtime services are controlled by the project.

Design ruleNative first. Compatibility layers are boundaries around the OS, not the definition of the OS.
PLATFORM

x86-64 native target

The kernel and desktop are designed around the x86-64 execution environment, with SMP, virtual memory, interrupts, native storage and graphics services forming the base.

RUNTIME

PS3-oriented subsystem

GameRunner models PS3 execution through PPU, SPU, DMA, JIT and RSX components rather than making the PS3 runtime the kernel itself.

02 · CORE

System Architecture

The architecture is layered. Boot establishes the kernel environment, the kernel owns execution and resource primitives, VFS and NYFS own storage, the graphics layer owns rendering, the compositor presents the desktop, and GameRunner consumes runtime services without replacing the kernel.

LIVE MERMAIDNative boot to desktop
flowchart TD
 A[UEFI / Firmware] --> B[Limine v12.9.0]
 B --> C[x86-64 Kernel Entry]
 C --> D[CPU + SMP]
 D --> E[Memory Manager]
 E --> F[Scheduler]
 F --> G[Kernel Services]
 G --> H[VFS]
 H --> I[NYFS]
 G --> J[Graphics HAL]
 J --> K[Compositor]
 K --> L[Desktop / Explorer]
BOOT

UEFI → Limine

Limine v12.9.0 supplies the framebuffer, memory map, HHDM, SMP/MP, module and RSDP information consumed by the native kernel.

KERNEL

Execution core

CPU/SMP, four-level paging, higher-half mappings, PMM, VMM, heap, scheduler, syscalls and user-fault isolation form the execution foundation.

USER SPACE

Desktop services

ELF processes, VFS, initramfs, NYFS, shell, Explorer, Settings, clipboard, input and GameRunner sit above explicit service boundaries.

PROCESS MODEL

ELF64 + per-process PML4

The ELF loader validates ELF64/x86-64 files, maps PT_LOAD segments into newly allocated user pages, creates a user stack and records the process entry and stack addresses. fork clones user-visible mappings into a child address space. Processes retain parent/child links, file tables, working-directory state, exit status and reaping state.

UACCESS

Kernel/user memory boundary

Syscalls enter through the x86-64 assembly entry path and are dispatched by the kernel. User pointers pass through the uaccess layer instead of being trusted directly. Current operations include process control, file operations, directory enumeration, mmap, exec, heap extension, time/sleep, signal/termination and NYFS file creation/removal.

DEVICES

Native device domains

Implemented domains include ACPI, AHCI, Intel e1000 detection/initialization, HDA audio initialization, PS/2 keyboard/mouse, USB/xHCI, and LAPIC/per-CPU/SMP infrastructure.

FILESYSTEM

VFS + initramfs + NYFS

VFS provides a VNode namespace and file-descriptor layer. The initramfs is a Limine-loaded ustar archive mounted at /. NYFS is mounted at /disk and currently uses a 512-byte superblock, fixed 64-entry file table and following data sectors.

IMAGE PIPELINE

Decode → pixel buffer → compositor

BMP, PNG, GIF, ICO and JPEG decoders feed Image Viewer and the Graphics API. The resulting pixels travel through the compositor to the framebuffer.

03 · CORE

Boot, Kernel and Init

The boot path is intentionally explicit: firmware, boot protocol, kernel entry, processor setup, memory setup, scheduler and system services. Current development includes init-program debugging before the next major GameRunner integration milestone.

  1. 1 · UEFIFirmware loads the Limine boot environment.
  2. 2 · LimineLoads notyvos-kernel.elf and configured modules.
  3. 3 · Boot requestsFramebuffer, memory-map, HHDM, SMP/MP, module and RSDP information is made available.
  4. 4 · _startKernel entry establishes the entry stack and transfers to kernel_main.
  5. 5 · kernel_mainSerial output, framebuffer console and logging become available.
  6. 6 · CPU + memoryCPU features, PMM, VMM, kernel heap and executable memory arena initialize.
  7. 7 · devicesACPI, AHCI, e1000, HDA, LAPIC/per-CPU, SMP and USB/xHCI domains initialize.
  8. 8 · NYFSNYFS mounts on the first available block device; development formatting occurs if no valid superblock exists.
  9. 9 · initramfsThe Limine module is parsed as ustar and mounted at /. NYFS is attached as /disk.
  10. 10 · compositorFramebuffer console switches into buffered desktop rendering.
  11. 11 · graphicsSoftware and VBE graphics backends register and initialize.
  12. 12 · PS3 runtimeTranslation cache and RSX state initialize, followed by decoder, ELF, PPU, SPU, DMA, JIT and RSX self-tests.
  13. 13 · schedulerThe task scheduler is initialized.
  14. 14 · init.elfinit.elf is loaded as an x86-64 user process with its own address space and user stack.
  15. 15 · interruptsInterrupts are enabled and the scheduler starts init.
  16. 16 · shellThe user shell becomes the primary interactive userland process.
ISO modulesCurrent boot media supplies notyvos-kernel.elf, init.elf and initramfs.tar. An optional converted wallpaper can also be included.
04 · CORE

Memory and Scheduler

MEMORY · 95%

PMM / VMM / heap

Physical memory management, virtual address management and dynamic allocation form the resource layer used by kernel services and higher-level components. Four-level paging and higher-half kernel mappings keep the kernel address space consistent across processes.

SCHEDULER · 85%

Task execution

The scheduler provides the execution boundary required for kernel work, services and future user programs. Init-program debugging remains the active milestone. User-fault isolation routes user-mode exceptions to the offending task.

05 · CORE

Storage, VFS and NYFS

VFS is the service-facing filesystem abstraction while NYFS is the native filesystem implementation. Explorer talks to the filesystem through this boundary rather than reaching directly into block-level details.

VFS

Stable service boundary

Kernel services and applications use a consistent filesystem interface, keeping the concrete filesystem implementation replaceable. VNode-based namespace and per-task file-descriptor tables provide the user-visible surface.

NYFS · 55%

Development filesystem

NYFS currently stores one 512-byte superblock, a fixed 64-entry file table and file data sectors. It supports create, read, write, directory enumeration and unlink. It is intentionally a small development filesystem, not yet a general-purpose journaling filesystem.

COMPOSITOR

Desktop scene

Desktop background, taskbar, Start menu, shortcuts, window focus/dragging, Alt-Tab, snap layouts, notification toasts, minimize/maximize/close and context menus.

WIDGETS

UI primitives

Button, Label and ListView primitives. Terminal, Explorer, Settings and Bin windows sit on the compositor.

THEMES

Appearance

Dark, Light and macOS Dark themes plus Appearance controls through Settings feed the active theme into the desktop UI styling layer.

07 · PS3

PS3 Runtime Architecture

The PS3 PPU state is represented by a register context containing GPR/FPR state, PC, LR, CTR, XER and CR plus memory/syscall callbacks. The baseline JIT looks up the current PPC PC in the translation cache, translates supported basic blocks, emits x86-64 machine code into executable memory and falls back to the interpreter for unsupported instructions.

LIVE MERMAIDPS3 runtime path
flowchart TD
 GAME[GameRunner] --> ABI[PS3 ABI]
 ABI --> PPU[PPU execution]
 ABI --> SPU[SPU execution]
 PPU --> JIT[JIT / translation]
 SPU --> DMA[DMA]
 PPU --> RSX[RSX]
 DMA --> RSX
 RSX --> HAL[Graphics HAL]
 HAL --> COMP[Compositor]
PPU

PowerPC

Decoder, interpreter and baseline x86-64 JIT with translation cache, block chaining and cache invalidation.

SPU

Local store

SPU interpreter with 256 KiB local store and mailbox foundations.

DMA

Cell-style

DMA queue, tag state and synchronization barriers between main memory and SPU local store.

RSX

Software path

FIFO, method decode, rasterization, textures, UVs, perspective correction, depth/scissor and mipmap/LOD sampling.

08 · PS3

GameRunner

GameRunner is the session-oriented surface for PS3 binary loading and runtime integration. The completed path covers format detection, PS3 ELF loading, ABI/syscalls, cellFs through VFS/NYFS and the PPU/RSX execution path. Phase 14 / 7D remains the next runtime integration milestone.

09 · DEVELOPMENT

Build and Toolchain

The project uses Clang/LLVM as the primary toolchain with CMake and Ninja. C++20 is the primary kernel language; userland components may use C17. Limine provides the boot protocol.

TOOLCHAIN

Clang + LLVM

Kernel and runtime components are built with Clang diagnostics and LLVM code generation. Assembly entry paths and linker scripts remain explicit.

LAYOUT

Source tree

Kernel, drivers, graphics, filesystem, PS3 runtime, userland and documentation live in clearly separated directories.

10 · DEVELOPMENT

Testing and Validation

Testing is layered so a failure can be isolated to boot, kernel, subsystem, desktop or runtime integration. Native tests and build validation are preferred over treating the complete ISO as the only test target. Every subsystem gets a boot self-test.

BUILD

Static validation

Compiler diagnostics, linker validation, source checks and build reproducibility. Warnings are errors; casts use static_cast.

RUNTIME

Boot validation

Kernel startup, init program, filesystem, graphics and GameRunner milestones are validated independently through self-tests and ISO runs.

11 · GRAPHICS

Fonts and Text Rendering

NotYVOS includes a native TrueType renderer. Inter-Regular is the default UI font. Text rendering feeds the compositor and is treated as part of the desktop graphics stack rather than a browser dependency. Multiple weights, kerning and complex-script shaping remain deferred.

14 · DECISIONS

Architecture Decision Records

These decisions document the binding technical choices that shape the system. They are intentionally short and concrete.

ADR-0001

Use Limine as the boot protocol

Limine provides a modern documented handoff into the native x86-64 kernel while keeping early boot code small.

ADR-0002

Use Clang + LLVM for the kernel toolchain

Clang/LLVM provides the primary C++ toolchain, diagnostics and code-generation infrastructure.

ADR-0003

AGPL-3 license

The OS source uses AGPL-3, while third-party components retain their own licenses.

ADR-0004

C++ is the primary language

C++ is primary; C, assembly, linker scripts and small utilities remain available where platform boundaries require them.

ADR-0005

PS3 firmware isolation

PS3 firmware is developer-supplied runtime input and is isolated from public source distribution.

ADR-0006

No Sony keys embedded

Protected Sony signing keys and equivalent private material are not embedded or distributed.

ADR-0007

Windows compatibility is a later boundary

Windows executable compatibility is separated from the native OS core and excluded from the current roadmap.

ADR-0008

Reserved domains are not created yet

Future network domains and services are documented as reserved names rather than existing services.

ADR-0009

Inter is the default UI font

Inter is the default TrueType UI font for a consistent desktop text baseline.

15 · SECURITY

Security, Firmware and Distribution Boundaries

PUBLIC SOURCE

No protected signing material

Protected Sony signing keys and equivalent private material are not embedded in the public repository.

FIRMWARE

Developer supplied

PS3 firmware is treated as developer-provided input to the runtime/build environment and is not presented as a publicly distributed project asset. NotYVFirm is a separate native firmware domain.

Compatibility boundaryWindows executable compatibility is not allowed to redefine the native kernel architecture. It is a separate compatibility concern with its own milestone boundary and is currently excluded from the roadmap.
